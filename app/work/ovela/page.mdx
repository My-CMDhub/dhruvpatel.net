## Two clocks

Every answer time on this page says which clock it is on.

The **caller's clock** starts at the caller's actual last word, measured from the recording. The **pipeline clock** starts later, when the speech model decides the caller has finished. On the same calls the caller's clock runs about 0.5–1.0 s longer, and most of that gap is not my code: it is end-of-turn detection, and the phone audio crossing from Australia to a US server and back.

So: a model that answered instantly would still leave a caller here waiting about 0.8 s. That is the floor this architecture has, and it is why the section below is about where a benchmark is held rather than which model wins.

## How it was earned

### A "yes" isn't agreement to everything

The booking tool trusted a flag the model filled in to say the summary had been read back. In 4 of 7 attempts it claimed a confirmation the caller never gave; in one, a "yes" to an email spelling booked a room. The gate now reads the transcript: a name, price and dates spoken by the agent, followed by the caller agreeing to *that*.

<L s="measured" n="7 attempts" src="readme" />

### A prompt rule is not a boundary

With the guest's name in the prompt behind a "do not reveal" rule, the agent volunteered it on the first turn in 4 of 5 replays. Now the lookup tool withholds the name, and code releases it only after identity is confirmed: 0 of 5. Four actions are gated in code the same way; tone stays in the prompt.

<L s="measured" n="5 replays" src="readme" />

### My own instrument was lying

The trace reader read one 100-row page and labelled it with the whole period I'd asked for. It reported a 3× slowdown that never happened, and it had also produced a "27% faster" claim, which I withdrew. Fixed and split by turn type, the honest picture is this: replies with no tool were already inside budget, and replies with a tool were not. The real win came from a per-call cache: a repeat booking lookup went from 1,073 ms to 0.4 ms.

<L s="withdrawn" n="replaced by the per-turn-type figures" src="readme" /> · <L s="measured" n="15 → 21 lookups" src="readme" />

### Same test, opposite winner

OpenAI is retiring the model Ovela ran on, so I benchmarked the replacement the careful way: the real 9,000-token prompt, all twelve tools, whole conversations with lookups and interruptions. From my laptop in Melbourne the new model was clearly faster — 1,234 ms to first token against 1,514 ms. I nearly shipped it on that.

The calls don't run in Melbourne. Re-run on the US server that actually answers the phone, the order reversed: 636 ms against 474 ms. The server's figure for the old model matched what live calls had already recorded, so that is the one I trust. The replacement's fast tier closed the gap to 535 ms, and that is what runs now.

I still can't fully explain why the order reversed. What I can say is that my desk was adding half a second to a second of distance to every request, and it wasn't landing equally on both models — the noise was bigger than the difference I was trying to measure.

<L s="measured" n="~400 requests per model on the laptop, ~250 on the server · median" src="readme" />

*A benchmark answers a question about the place it ran. Mine had been held at my desk.*

### The goodbye nobody said

Swapping the model changed behaviour the code had silently depended on. The new one ended calls by calling `hang_up_call` without saying anything first — it put the goodbye inside the tool's arguments, where nothing spoke it. The turn then sat for up to 15 s waiting on audio nobody had asked for, and when the caller said "Hello?" into that silence, it cancelled the hang-up mid-request. Three goodbyes, and the caller hung up first.

Now the code speaks the tool's own farewell when the model didn't, a hang-up can't be cancelled by whatever the caller says next, and a turn with no words in it ends at once.

<L s="measured" n="one live call before, one after · 5 regression tests, each failing without the fix" src="readme" />

### What did the caller actually hear?

Text is generated faster than it's spoken. When a caller cuts in, the model has "said" words the caller never heard. Ovela keeps only the part that played. And "mhmm" isn't an interruption.

The count this section used to quote was wrong, and I found out the same way I find out most things. A two-channel recording of one call showed the caller spoke over the agent **once**; the log had counted seven. The other six fired after the agent had already finished — the caller answering its question, inside a two-second margin left over from an older design. The margin is now 0.8 s, sized to the 0.24–0.87 s audio delay I measured, and the fix is written and tested but not yet confirmed on a live call.

### Silence while a tool runs

When the model reached for a tool, the caller heard nothing for 2.3–4.3 s. Now code says a short line first ("Let me have a look."), and the caller hears a first word in 0.7–0.8 s. The answer itself still waits on the tool; the silence is gone.

## What stands

- No-tool replies start 0.6–0.8 s after the speech model calls the turn over.
- Identity: 24 of 28 real guests found from misheard details, 0 of 8 non-guests invented, 0 wrong guest.
- Four actions gated in code.
- 1,949 tests.

## What it still doesn't do

- **Tool replies take {s.ledger.at(-1).value}.** The remaining latency is the tool round trip, not the model.
- **Identity is confirmed on one matching word of the name**, so a relative sharing the surname passes.
- **Gates judge agreement from word patterns**, so an unusual "yes" can be refused.
- **No caller has ever been a stranger.** Every call is mine, or a script's.
- **One tenant, no real customers.**
