## How it was earned

### Choosing the model on the real constraint

The assistant ran on Llama 3.1 8B, quantised to 4-bit, on a single 16 GB GPU. That GPU was the constraint, so the first filter was arithmetic: at full 16-bit precision, neither Llama 3.1 8B, Qwen 2.5 7B nor a DeepSeek R1 distill of the same size loads with room left to answer anyone.

The surprise is the last two rows. Qwen at 8-bit has bigger weights than Llama at 4-bit, yet leaves more room for context: its memory per token of context is less than half Llama's, with 4 key-value heads to Llama's 8 and 28 layers to 32. Better precision cost us no context.

I stress-tested the ones that fit. The 14B loaded but barely ran. Among the rest we ranked latency first, then how well the model stayed inside the assistant's scope and followed its output format, then how it handled the code and reasoning that web-security questions need. Qwen 2.5 7B at 8-bit won on all three. I made the switch in October 2025, set its context window deliberately smaller than the room it had, to keep memory headroom, and tuned vLLM's settings for latency.

So that speed was measured rather than felt, the assistant logs time to first token and tokens per second on every answer.

### Guarding a stream without new compute

The model is treated as untrusted. A jailbreak check runs on every question before anything is generated, and the answer is checked for jailbreaks and for staying on web security before the user sees it.

The catch: the open-source guardrails framework we used checked a finished answer, not a stream. Waiting for the whole answer meant a blank screen, and on the CPU we had, the topic check took tens of seconds per answer. A GPU for the checks was the obvious fix, and it wasn't coming soon.

So I streamed the answer and checked it in pieces. Text is held back until a few sentences are complete, which gives the small classifier models enough context to judge. Each piece is checked in the background while the next one streams, and the stream stops the moment a piece fails. People see an answer start almost at once. The trade-off, chosen on purpose: a violation can surface a sentence or two in, rather than never being shown at all.

Before release I ran it against more than 140 adversarial prompts, from prompt injection and role-play to emotional manipulation and multi-step attacks, and checked each refusal held.

### Not reaching for a vector database

The assistant answers questions about *this* user's scan. That data was already structured in the database, and the general knowledge it needed was small and predictable. So context came straight from the scan records and a small fixed knowledge base. A vector store would have been one more service to run and keep in sync, for a worse answer: similar documents instead of the exact scan.

### Debugging past my own component

Users on the scanner's no-SSL path waited more than five minutes for an SSL/TLS result that never arrived. The scan wasn't slow; it had never started. That path marked the request complete without ever queuing an SSL scan. I made it queue a linked background SSL scan and put its result on the report when it finishes.

## What stands

Still in the live product, although some layouts have changed since:

- the assistant, on the scan results;
- the SSL/TLS scan fix;
- the certification offered to sites that score 4+ out of 7;
- technology detection (WebAnalyze) and JavaScript vulnerability detection (RetireJS);
- security headers and frontend changes.
